# VIP code analysis: code to specification (reverse run)

## Language convention

Use precise scientific and engineering English for skill instructions, technical clarifications, review gates, plans, reports, VIP code comments, and script messages. Distinguish observed results from assumptions. Bilingual English–Vietnamese content is reserved for README files and documents explicitly designated as user guidelines.

`vip` means `python3 scripts/vip.py` in this skill folder.

## Rules

- The code is evidence of what the VIP does, not of what the standard requires. A behavior that contradicts the standard is a finding for the user, never a requirement.
- Never modify the user's code. The scan is read-only and lexical; it needs no simulator and no dependencies. Say what a lexical scan can miss (macro-generated and generate-block constructs).
- Every cell derived from code carries `UNVERIFIED` and a pointer `CODE:<file>:<line>:<label>`. Remove the word `UNVERIFIED` only after the row is checked against the standard or accepted by the user; keep the pointer, so `vip verify-code` can detect drift later.
- Do not invent clause numbers, strengths, or boundaries. Ask once, in one question, for the standard file and revision; record unanswered points as `DEC-nnn` rows of type Open.
- Gate 1 is refused while `UNVERIFIED` remains (`--allow-unverified` needs a note that lists what stays unverified).
- Never overwrite an output; the run directory is numbered.

## Workflow

1. Ask once: code directory, VIP tag (2 to 8 lowercase letters), standard file and revision, roles in scope. Then `vip init <root> <tag> --mode reverse --code <dir>` (the command line of the flow skill; `vip next` shows the state afterwards).
2. `vip inventory` scans the code and prints a summary. Use `vip inventory show <kind> [--grep T] [--limit N]` for one kind of fact (`classes`, `assertions`, `signals`, `messages`, `todos`, ...) instead of opening files.
3. `vip from-code --title "<name>" --standard "<id rev>"` writes the draft specification and `00_code/draft_report.md` (what was derived, what could not be). Options `--interface`, `--item`, `--cfg` select the main interface, item class, and configuration class when the inventory has several.
4. Review in this order, opening only the CODE region of each row: signals, parameters, roles and profiles, requirements and their Section 8.1 expressions, capabilities, knobs, monitors. Correct the row, then remove `UNVERIFIED`. Fill what code cannot show: standard references, clause of each requirement, strength, boundaries (Section 5.6), error injections (Section 6.3), decisions.
5. Compare the findings with the standard: a check that is stricter, weaker, or missing against the standard is listed in the report as a finding with the requirement, the code location, and the standard clause. Do not fix code in this run.
6. `vip verify-code` (pointers still match) and `vip validate` (template rules). Repeat until both exit 0.
7. Gate 1 with the user: present the specification, the open decisions, and the findings. Record `vip gate G1 APPROVED --by <NAME>` only after the user replies APPROVE.
8. `vip adopt` copies the code into `04_vip/<tag>_vip`. The next runs start from this run: `vip init <root> <tag> --mode bugfix --base-run <run>` or `--mode feature`.

If the code was generated by this flow (it has `spec/vip_generation.json`), the run is not needed: the specification is `spec/` of the VIP and the layout is `flow`.

## Token discipline

Read the summary and one kind of fact at a time; never open the whole tree. Quote counts, IDs, and `file:line`, not code. A 130-class VIP is analyzed with about ten short commands.

## Final response

Specification path, counts (signals, requirements, expressions, capabilities, knobs), `UNVERIFIED` marks left, findings against the standard, open decisions, `vip validate` and `vip verify-code` results, Gate 1 status, adoption status, and `NOT_RUN` items (no simulation is part of this skill).

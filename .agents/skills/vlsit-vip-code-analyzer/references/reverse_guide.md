# Reverse guide: from VIP code to an as-built specification

## 1. What the inventory records

`vip inventory` scans `.sv`, `.svh`, `.v`, `.vh` files lexically (comments are blanked, regular expressions run on the rest). It never compiles and never modifies the code. Each fact carries `file` and `line`.

| Kind (`vip inventory show <kind>`) | Content |
|---|---|
| `files`, `units` | files with line counts; interfaces, modules, packages |
| `signals`, `parameters`, `interfaces` | interface signals with width and direction, parameters with defaults, clocking blocks, modports |
| `assertions` | SVA properties and the `VLSIT_VIP_CHK_*` macros: label, severity, message, property text |
| `covergroups` | covergroups with their coverpoints and crosses |
| `classes` | every class with its role: `agent`, `driver`, `monitor`, `sequencer`, `item`, `config`, `coverage`, `sequence`, `env`, `scoreboard`, `test`, `other`; the role comes from the base-class chain, typedef aliases, then the class name (`role_basis` says which) |
| `config_fields`, `item_fields` | fields of configuration and item classes (`rand` marked) |
| `messages`, `config_db`, `todos`, `defines` | `uvm_error/warning/fatal` IDs, config_db keys, TODO and FIXME markers, compile-time defines |

A lexical scan can miss constructs that macros or generate blocks produce, and it cannot resolve inheritance across files it did not scan. Say so in the report when a count looks low (for example 0 assertions in a class-based VIP: its checks are probably in monitor code, see section 3).

## 2. What the draft specification contains

| Specification part | Derived from | Marking |
|---|---|---|
| Section 4.3 signals | the main interface | each row `UNVERIFIED`, `CODE:` pointer to the declaration; the driver column is a guess from names (master, slave) |
| Section 4.2 parameters | interface and package parameters, named `PARA_<NAME>` | `UNVERIFIED` |
| Section 6.1 items, 7.1 knobs | item and configuration class fields | `UNVERIFIED` |
| Section 6.2 capabilities, 10 sequences | sequence classes | one CAP row per sequence |
| Section 6.4 monitors | monitor classes | `UNVERIFIED` |
| Sections 5.x requirements, 8.1 expressions | labeled assertions; strength from severity (error: MUST, warning: SHOULD); a single-cycle implication becomes a Section 8.1 expression; an explicit check ID in the label is kept | `UNVERIFIED`, `CODE:<file>:<line>:<label>` in Notes |
| Section 14 decisions | open questions: the standard and its revision, clause numbers, ambiguous roles | type Open |

Everything the code cannot show stays a placeholder that `vip validate` reports: standard references and clause numbers, boundaries (5.6), injections (6.3), reset values, legal parameter ranges.

## 3. Review order and rules

1. Signals, parameters, roles, profiles: the standard decides, the code is a hint. Fix names, widths, directions, and reset values from the standard.
2. Requirements: for each derived row confirm (a) the standard has this rule, (b) the strength, (c) the clause, (d) the expression says what the standard says. A check that is stricter or weaker than the standard, or a rule the code does not check, is a **finding**: list it in the as-built report with the requirement, the code location, and the clause. Do not change the code in a reverse run.
3. Checks that are not assertions (class-level checks in monitors, scoreboards): `vip inventory show messages --grep <ID>` finds the error IDs; add a requirement with Check type `CLASS` and a `CODE:` pointer to the class.
4. Unlabeled assertions are listed in `00_code/draft_report.md`; add a label in the notes of the requirement they belong to or record them as a finding.
5. Capabilities, knobs, items, monitors: keep what users of the VIP can observe; drop internal helpers.
6. Remove the word `UNVERIFIED` only from a row that was checked. Keep the `CODE:` pointer.

## 4. Drift

`vip verify-code` re-reads each `CODE:` pointer and reports a requirement whose label is no longer near the recorded line. Run it after any edit of the code, and before Gate 1.

## 5. Finishing

Gate 1 needs a specification that validates and has no `UNVERIFIED` left. If some rows cannot be verified yet (no standard at hand), approve with `--allow-unverified` and a note that lists them; they stay visible in the specification. `vip adopt` then copies the code into the run as the base tree. Later runs: `--mode bugfix` or `--mode feature` with `--base-run <this run>`; code that was not generated by this flow has layout `external` (no plan, no generated tree, evidence is the project's regression report).
